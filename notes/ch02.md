# Chapter 2: Logging

## 2.1 Logging in Go

Linko change: in `main.go`, `auth.go`, `server.go` and `handlers.go`, replace
`fmt.Println` with `log.Println`, and `fmt.Printf` and
`fmt.Fprintf(os.Stderr, ...)` with `log.Printf`, dropping the `\n`.

Notes:

- The submit runs five checks: Linko is running, the code uses the `log`
  package, `fmt` logging calls were removed, shut down Linko, and the startup
  and shutdown messages are present. The `fmt` check passed with
  `store.go:109` unchanged, so it covers only the four files the lesson names.
- Measured: the default `log` logger writes to stderr, not stdout. With
  stdout and stderr captured to separate files, stdout was empty and every
  line, including the 1.3 lifecycle lines, was on stderr. The lesson's
  `2>&1 | tee` merges the two, so the move does not show there.
- Measured: each line gets a `2026/11/13 13:54:18` prefix (`log.LstdFlags`):
  local time, one-second resolution, no zone. `log.Printf` appends `\n` only
  when the message lacks one.
- Measured: `internal/store/store.go:109` still logs with `fmt.Printf`. The
  lesson names only the four files above, so it is left as is.
- Measured: a request as `saruman` (whose stored hash is `invalidFormat`)
  returns 500 and logs the same bcrypt error twice, once in
  `validatePassword` and once in `authMiddleware`. This is the starter's
  deliberate redundant log line. With timestamps, the two lines share a
  second and read as one event logged twice.
- Reasoned, not measured: `log.Fatal` calls `os.Exit(1)`, which skips
  deferred calls. Keep it out of `run`, where the deferred `cancel` and the
  graceful shutdown live.
- Production note (reasoned, not measured): timestamps help diagnosis
  (ordering, matching against other systems), but `log` has no levels, so
  nothing can filter errors from noise for detection. For devices, prefer
  `log.LUTC|log.Lmicroseconds`, or let journald stamp the line: local time
  with no zone and one-second resolution does not line up with a backend's
  logs, and a device clock may not be synced yet at boot.

## 2.2 Use the Logger

Linko change: add a package-level
`var logger = log.New(os.Stderr, "DEBUG: ", log.LstdFlags)` in `main.go` and
route every `log.X` call in `main.go`, `server.go`, `handlers.go` and
`auth.go` through it.

Notes:

- The submit runs three checks: Linko is running, shut down Linko, and
  debug messages are logged. What the last one matches is not shown; the
  `DEBUG: ` prefix is the likely target (reasoned, not measured).
- Measured: every line now reads
  `DEBUG: 2026/11/15 13:57:47 Linko is running on http://localhost:18899`.
  The prefix goes before the timestamp. With `log.LstdFlags|log.Lmsgprefix`
  it moves after it: `2026/11/15 13:57:55 DEBUG: with Lmsgprefix`.
- Measured: stdout stayed empty (0 bytes); everything is on stderr, as
  before. 2.1's default logger already wrote to stderr, so this lesson only
  makes the destination explicit.
- The prefix is fixed per logger, so the bcrypt error and the startup line
  both say `DEBUG:`. A prefix is not a level: `log` cannot filter by it.
  Levels arrive with `slog` in chapter 3.
- The logger is a package-level global on purpose; 2.4 ("Global Logger vs.
  Dependency Injection") replaces it.
- The lesson suggests golangci-lint's `forbidigo` with
  `pattern: ^fmt\.Print.*$` to catch stray `fmt` logging. It is enabled in
  `.golangci.yml`. Measured with golangci-lint v2.15.0: the lesson's config
  as given reports nothing new, because v2 only runs linters in the
  `standard` set unless they are listed under `linters.enable`. With
  `enable: [forbidigo]` it reports
  `internal/store/store.go:109:3: use of fmt.Printf forbidden because "Use logger instead."`.
  That line is starter code outside the lesson's four files, so it stays and
  the lint baseline is now 6 errcheck plus 1 forbidigo.
- The pattern matches `fmt.Print`, `Printf` and `Println` only. It does not
  match `fmt.Fprintf(os.Stderr, ...)`, which 2.1 also counted as logging.
- Production note (reasoned, not measured), for detection: a constant
  `DEBUG:` on error lines works against detection. Anything that greps or
  alerts on severity sees every line as debug. Until levels exist, the
  prefix tells you which logger wrote a line, not how bad it is.

## 2.3 Logging Requests

Linko change: add `requestLogger(logger *log.Logger) func(http.Handler) http.Handler`
in `middleware.go`. It calls `next.ServeHTTP(w, r)`, then logs
`Served request: METHOD Path`. `newServer` wraps the whole mux with it, so
every route is logged.

Notes:

- The submit runs four checks: Linko is running, reject unauthenticated
  access to statistics, shut down Linko, and check both requests were
  logged. Reasoned, not measured: "both requests" are the stats request and
  the shutdown request, so the stats line must be logged even though
  `authMiddleware` rejects it before the handler runs. It is, because the
  request logger wraps the whole mux, outside the auth middleware.
- Measured: one line per request, after the handler's own lines:
  `DEBUG: 2026/11/16 12:48:06 Served request: POST /api/shorten` follows the
  three shortening lines. `POST /admin/shutdown` is logged before
  `Linko is shutting down`: the middleware returns before `Shutdown` drains
  the connection.
- Measured: a 404 (`GET /NOPE`), a 401 (`GET /api/urls` with a wrong
  password) and a 405 (`PUT /`) log exactly like a 200. The line has no
  status and no duration, so it says a request happened, not how it went.
- Measured: `GET /?q=secret-token` logs `GET /`. `r.URL.Path` drops the query
  string, which keeps tokens in query parameters out of the log.
- Measured in a scratch program (Go 1.27): `http.ServeMux` sets `r.Pattern`
  on the same `*http.Request` the middleware holds, so after
  `next.ServeHTTP` the middleware can read `GET /{shortCode}` for
  `/ABC123`. Before the call it is empty; for a path no route matches it
  stays empty. The pattern is the low-cardinality form of the path, which is
  what a metric label needs in chapter 9.
- Reasoned, not measured: logging after `next.ServeHTTP` means a handler
  that panics is never logged here. `net/http` recovers the panic per
  connection and the middleware's line is skipped.
- Production note (reasoned, not measured): this line answers neither
  question well yet. For detection it needs the status code (wrap
  `http.ResponseWriter` to capture `WriteHeader`), so 5xx can be counted.
  For diagnosis it needs duration and a request ID that the handler's own
  lines also carry; without one, two concurrent shortens interleave and
  cannot be told apart.

## 2.4 Global Logger vs. Dependency Injection

Linko change: remove the global `logger`. `run` builds two loggers and
injects them: an access logger writing to `linko.access.log` with `INFO: `,
passed to `newServer` (request, handler and startup lines), and a standard
logger on stderr with `DEBUG: `, passed to `store.New` and used for the
shutdown messages. `server` and `Store` each get a `logger *log.Logger`
field.

Notes:

- Measured: with a short code's file made unreadable, one failure lands in
  two sinks. stderr gets
  `DEBUG: … failed to read …/data/ESE5HN: … permission denied` from the
  store, and `linko.access.log` gets
  `INFO: … failed to lookup URL: … permission denied` from the handler. The
  only link between them is the timestamp.
- Measured: handler errors (bcrypt failures, lookup failures) go through the
  access logger, so they carry `INFO:`. As in 2.2, the prefix names the
  destination, not the severity.
- Measured: `Linko is running on …` now goes to `linko.access.log`, so the
  terminal shows nothing at startup and only `Linko is shutting down` at
  exit. This follows the spec (server logs to the access logger).
- Measured: `linko.access.log` is opened relative to the working directory,
  not the `-data` directory. Run from a read-only directory, Linko exits 1
  with `DEBUG: … failed to create access log file: open linko.access.log: permission denied`.
  The first draft printed that with `fmt.Fprintf` and no `\n`, so the shell
  prompt ran onto the same line; creating the standard logger first and
  using it for the file errors fixed both that and the `fmt` import.
- Measured: injecting a logger into `Store` removes the last `fmt.Printf`
  log call (`store.go:109`), so the forbidigo issue from 2.2 is gone.
- Reasoned, not measured: `*log.Logger` serialises writes with a mutex, so
  concurrent handlers sharing the access logger do not interleave within a
  line. The race detector reported only the starter's `serverErr` race.
- Production note (reasoned, not measured): injection is what makes
  per-component loggers possible, which helps diagnosis (you know which part
  wrote a line). The cost shows here: splitting by component without a
  shared request ID scatters one failure across files. With `slog`, inject
  one logger and derive per-component ones with `With("component", …)` into
  the same sink, so filtering is a query, not a file choice.

## 2.5 Logger Configuration

Linko change: one logger for the whole program, built by
`initializeLogger() (*log.Logger, closeFunc, error)` in `logger.go`. With
`LINKO_LOG_FILE` set it writes to `io.MultiWriter(os.Stderr, file)`;
without it, to stderr only. No prefix. `run` defers the returned close
function and replaces 2.4's two loggers with it.

Notes:

- Measured: with `LINKO_LOG_FILE=linko.access.log`, stderr and the file get
  the same four lines, byte for byte, from startup to
  `Linko is shutting down`. Unset, the lines go to stderr only.
- Measured: `LINKO_LOG_FILE=` (set but empty) exits 1 with
  `failed to create logger: creating log file: open : no such file or directory`.
  `os.LookupEnv` reports an empty variable as set. Kept on purpose: the
  lesson says "if it is set", and a misconfigured empty value fails loudly
  at start instead of silently dropping the file. `os.Getenv(...) != ""`
  would treat empty as unset.
- Measured: an unwritable path exits 1 with
  `failed to create logger: creating log file: open /proc/nope.log: no such file or directory`.
- `initializeLogger` returns the file's `Close` instead of calling
  `log.Fatalf` as the lesson's sample does. `log.Fatalf` calls `os.Exit`,
  which skips `run`'s deferred calls.
- `os.Stderr` must stay first in the `MultiWriter`. `go doc io.MultiWriter`:
  "If a listed writer returns an error, that overall write operation stops
  and returns the error; it does not continue down the list." With the file
  first, a full disk would also silence stderr, and `log.Logger` discards
  the write error, so nothing would report it.
- Production note (reasoned, not measured), for diagnosis: one logger
  feeding several sinks replaces 2.4's split files, so every line is whole
  in every sink and nothing has to be stitched back together by timestamp.
  Choosing sinks by environment variable matches how devices and containers
  are configured. On a journald target, stderr alone is usually enough; a
  second copy in a file costs flash writes for no gain.
