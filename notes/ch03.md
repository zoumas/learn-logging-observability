# Chapter 3: Structured Logging

## 3.1 Structured Logging

Quiz.

- Q: Which is the biggest "killer feature" of structured logging?
  A: Key/value pairs that can be easily parsed, stored, and queried in
  different formats.

Notes:

- The lesson contrasts a raw line with metadata buried in the message
  (`User 9284 failed to login at ... from IP address ...`) with
  `slog.Error("login failed", "user_id", 9284, ...)`. The call site names the
  fields; the handler picks the format (text or JSON). Human readability is
  a property of the text handler, not the feature.
- Measured (Go 1.27): the same call through three handlers:

  ```text
  2026/11/17 22:20:03 ERROR login failed user_id=9284 ip_address=102.32.21.192
  time=2026-11-17T22:20:03.982+02:00 level=ERROR msg="login failed" user_id=9284 ip_address=102.32.21.192
  {"time":"2026-11-17T22:20:03.982916006+02:00","level":"ERROR","msg":"login failed","user_id":9284,"ip_address":"102.32.21.192"}
  ```

  The default `slog` logger (no handler set) goes through the `log` package,
  so it keeps the `log.LstdFlags` prefix and prints attrs as `key=value`
  without the `time=`/`level=`/`msg=` keys. `TextHandler` uses RFC 3339 with
  milliseconds and zone; `JSONHandler` uses nanoseconds. JSON keeps
  `user_id` a number.
- Measured: a dangling key, `slog.Error("odd", "user_id")`, logs
  `!BADKEY=user_id`. The alternating `...any` form fails at run time, not
  compile time. Measured: `go vet` reports `call to slog.Error missing a final value`;
  `slog.Int`/`slog.String` or `LogAttrs` avoid it.
- The lesson's example also passes a `"timestamp"` attr, which duplicates
  the handler's own `time` key. Let the handler stamp the record.
- Production note (reasoned, not measured): structured fields answer
  diagnosis. Filtering by `user_id` or device ID across a fleet becomes a
  query, not a regex over prose. They also feed detection: an aggregator can
  count `level=ERROR` per field without parsing messages. Where it falls
  short: fields only help if names are consistent across services (`user_id`
  vs `userId` split the query), and high-cardinality values belong in logs,
  not later in metric labels.

## 3.2 Slog Package

Linko change: `*log.Logger` becomes `*slog.Logger` built with
`slog.NewTextHandler(w, nil)`, in `initializeLogger`, the server, the
request middleware and `store.New`. Each `Printf` becomes
`Info(fmt.Sprintf(...))`, as the lesson asks. Key/value attributes come in
3.5.

The CLI check needs Linko running on `localhost:8899`, then checks that the
code imports `log/slog` and no longer imports `log`. It does not read any
log output, so a `!BADKEY` line would still pass. Only `go vet` catches it.

Notes:

- slog has no `Infof`. Arguments after `msg` are key/value pairs, so a
  converted `Println` call is a trap:
  `s.logger.Info("Shortening URL:", longURL)` compiles and runs. Measured:

  ```text
  level=INFO msg="Shortening URL:" !BADKEY=https://example.com
  ```

  A lone value with no key becomes `!BADKEY`. Nothing fails at runtime. The
  line just loses its key.
- Measured: `go vet` catches it
  (`call to slog.Logger.Info missing a final value`), and golangci-lint's
  govet reports the same. Keep vet as a gate. It is the only thing that
  stops a malformed call from shipping.
- Every line is `level=INFO` for now, including the store lookup failure,
  the shutdown failure and the bcrypt error. Detection: an alert on
  `level=ERROR` would never fire. 3.3 and 3.4 fix the levels.
- Measured: the starter's `serverErr` race in `main.go` still shows under
  `go build -race` after `POST /admin/shutdown` (now lines 48 and 60).
  Nothing new.

## 3.3 Log Levels

Linko change: `initializeLogger` builds a stderr `TextHandler` at
`slog.LevelDebug` and, when `LINKO_LOG_FILE` is set, a file `TextHandler`
at `slog.LevelInfo` over the 8 KiB buffer, combined with
`slog.NewMultiHandler` (new in Go 1.26) into one logger. The startup and
shutdown lines move to `Debug`; every error path (store creation, shutdown,
server error, lookup, list, the two bcrypt lines) moves to `Error`.

Notes:

- Measured: the same run gives stderr 13 lines and the file 11. The file
  has everything except the two `level=DEBUG` lifecycle lines. Without a
  file, stderr gets all levels.
- Measured: the store lookup failure and the handler's report of it are now
  both `level=ERROR`, as are the two bcrypt lines (the starter's deliberate
  duplicate). An alert counting `level=ERROR` counts each failure twice.
- `slog.MultiHandler` is not `io.MultiWriter`. From the Go 1.27 source
  (`log/slog/multi_handler.go`): `Handle` calls every enabled handler with
  `r.Clone()`, collects errors, and returns `errors.Join(errs...)`; it does
  not stop at the first error. So 2.5's rule "keep `os.Stderr` first" no
  longer matters: a failing file handler cannot silence stderr.
- From the same source (`log/slog/logger.go:264`): `Logger` discards the
  error, `_ = l.Handler().Handle(ctx, r)`. A failing file still goes
  unreported until the flush at exit (2.8).
- `MultiHandler.Enabled` returns true if any child is enabled, so a `Debug`
  call is always built and passed down while stderr is at `LevelDebug`; each
  child then checks its own level before handling.
- Production note (reasoned, not measured): levels are the first tool here
  that serves detection directly, since a filter or alert can key on
  `level=ERROR`. Two gaps remain. The duplicate error lines inflate any
  count, so log an error once, where it is handled. And with lifecycle lines
  at `Debug`, the file never records a start or stop: a restart shows up
  there only as a gap in timestamps. On a device, a restart loop is
  something to detect, so keep the start line at `Info`.

## 3.4 More Log Levels

Quiz. The lesson's guidance, per level:

- Debug: detail needed only while debugging; usually off in production.
- Info: notable events that are not errors (a login, a config load, a server
  start). Many can be replaced by aggregated metrics.
- Warn: avoid it. Decide instead: a potential bug is `Error`; something the
  user must know gets a 4xx response and `Info`; something that resolves
  itself is not logged.
- Error: system failures, with enough context to diagnose them (the error,
  a stack trace, who and what was involved).
- 5xx responses are system errors and log at `Error`. 4xx responses are user
  errors and log at `Debug` or `Info`, or not at all.

Q: A user requests a resource that doesn't exist and receives a 404
response. What is the most appropriate log level for this event?
A: Debug: the system handled the request correctly; this is a client
error, not a system failure.

Notes:

- Linko after 3.3 already follows this. A missing short code returns 404
  and logs nothing beyond the `Info` request line; a wrong password returns
  401 and logs nothing. The `Error` lines all sit on 500 paths: the bcrypt
  failure, the unreadable store file, the list failure.
- Production note (reasoned, not measured), for detection: a single 4xx is
  not an error, but a rate of them can be. A jump in 401s after a
  certificate or credential rotation means a fleet of devices can no longer
  authenticate; a jump in 404s after a deploy means broken links. Count 4xx
  by route and status as a metric (chapter 9) and alert on the rate, rather
  than raising each one to `Error` and paging on noise.
