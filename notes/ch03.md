# Chapter 3: Structured Logging

## 3.1 Structured Logging

Quiz.

- Q: Which is the biggest "killer feature" of structured logging?
  A: Key/value pairs that can be easily parsed, stored, and queried in
  different formats.

Notes:

- The lesson contrasts a raw line with metadata buried in the message
  (`User 9284 failed to login at ... from IP address ...`) with
  `slog.Error("login failed", "user_id", 9284, ...)`. The call site names the
  fields; the handler picks the format (text or JSON). Human readability is
  a property of the text handler, not the feature.
- Measured (Go 1.27): the same call through three handlers:

  ```text
  2026/11/17 22:20:03 ERROR login failed user_id=9284 ip_address=102.32.21.192
  time=2026-11-17T22:20:03.982+02:00 level=ERROR msg="login failed" user_id=9284 ip_address=102.32.21.192
  {"time":"2026-11-17T22:20:03.982916006+02:00","level":"ERROR","msg":"login failed","user_id":9284,"ip_address":"102.32.21.192"}
  ```

  The default `slog` logger (no handler set) goes through the `log` package,
  so it keeps the `log.LstdFlags` prefix and prints attrs as `key=value`
  without the `time=`/`level=`/`msg=` keys. `TextHandler` uses RFC 3339 with
  milliseconds and zone; `JSONHandler` uses nanoseconds. JSON keeps
  `user_id` a number.
- Measured: a dangling key, `slog.Error("odd", "user_id")`, logs
  `!BADKEY=user_id`. The alternating `...any` form fails at run time, not
  compile time. Measured: `go vet` reports `call to slog.Error missing a final value`;
  `slog.Int`/`slog.String` or `LogAttrs` avoid it.
- The lesson's example also passes a `"timestamp"` attr, which duplicates
  the handler's own `time` key. Let the handler stamp the record.
- Production note (reasoned, not measured): structured fields answer
  diagnosis. Filtering by `user_id` or device ID across a fleet becomes a
  query, not a regex over prose. They also feed detection: an aggregator can
  count `level=ERROR` per field without parsing messages. Where it falls
  short: fields only help if names are consistent across services (`user_id`
  vs `userId` split the query), and high-cardinality values belong in logs,
  not later in metric labels.

## 3.2 Slog Package

Linko change: `*log.Logger` becomes `*slog.Logger` built with
`slog.NewTextHandler(w, nil)`, in `initializeLogger`, the server, the
request middleware and `store.New`. Each `Printf` becomes
`Info(fmt.Sprintf(...))`, as the lesson asks. Key/value attributes come in
3.5.

The CLI check needs Linko running on `localhost:8899`, then checks that the
code imports `log/slog` and no longer imports `log`. It does not read any
log output, so a `!BADKEY` line would still pass. Only `go vet` catches it.

Notes:

- slog has no `Infof`. Arguments after `msg` are key/value pairs, so a
  converted `Println` call is a trap:
  `s.logger.Info("Shortening URL:", longURL)` compiles and runs. Measured:

  ```text
  level=INFO msg="Shortening URL:" !BADKEY=https://example.com
  ```

  A lone value with no key becomes `!BADKEY`. Nothing fails at runtime. The
  line just loses its key.
- Measured: `go vet` catches it
  (`call to slog.Logger.Info missing a final value`), and golangci-lint's
  govet reports the same. Keep vet as a gate. It is the only thing that
  stops a malformed call from shipping.
- Every line is `level=INFO` for now, including the store lookup failure,
  the shutdown failure and the bcrypt error. Detection: an alert on
  `level=ERROR` would never fire. 3.3 and 3.4 fix the levels.
- Measured: the starter's `serverErr` race in `main.go` still shows under
  `go build -race` after `POST /admin/shutdown` (now lines 48 and 60).
  Nothing new.
