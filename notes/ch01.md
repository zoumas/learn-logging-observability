# Chapter 1: Observability

## 1.1 Welcome to Logging and Telemetry

CLI lesson: install the Boot.dev CLI, `bootdev login`, then run the lesson's
check. The check passes when the output contains
`Wait, it's just standard out? Always has been.`

Notes:

- `bootdev run <id>` runs the checks without submitting. `bootdev run -s <id>`
  submits and marks the lesson complete. The command for each lesson is in the
  test panel, behind the login.
- Measured: `bootdev --version` prints `bootdev version v1.32.5`.
- Measured: after the 1.1 submit, the CLI said v1.32.6 was available.
  `bootdev upgrade` installs it with `go install`; `bootdev --version` then
  prints `bootdev version v1.32.6`.
- The course's two questions, which I apply to every production service:
  1. How do I know when something is going wrong? (detection)
  2. How can I identify the problem as quickly as possible? (diagnosis)
- Reasoned, not measured: the pillars split across the two questions.
  Detection needs signals that are cheap to evaluate all the time: metrics
  and the alerts built on them, keyed on symptoms users feel (error rate,
  latency, saturation), not on causes. Diagnosis needs detail joined by an
  ID: structured logs with request context, traces across services, and
  profiles for CPU and memory. A log line nobody is alerted to does not
  answer question 1; a counter with no labels to slice by does not answer
  question 2.
- Production note (reasoned, not measured): for a device fleet, question 1
  includes silence. A device that stops reporting produces no errors, so
  detection needs an absence check (time since last heartbeat per device),
  and a consumer that stops needs queue depth or consumer lag on the broker.

## 1.2 Linko Overview

CLI lesson: clone `bootdotdev/linko-starter`, run `go run .`, and submit the
check with Linko serving on `http://localhost:8899`.

Notes:

- This repository is the starter with its history kept. `upstream` points at
  `bootdotdev/linko-starter`, so a fix to the starter can be merged in later.
- The starter keeps the module path `boot.dev/linko` (it reverted a rename in
  `3557170`). Renaming it would rewrite every internal import for no gain.
- The course says the starter has deliberate bugs and oddities, to be found
  with observability later. Do not fix them early.
- Measured on `36bba29`: `go build -race`, run, `POST /admin/shutdown`. The race
  detector reports a data race on `serverErr` in `main.go`. The server
  goroutine writes it (`serverErr = s.start()`) and `run` reads it after
  `<-ctx.Done()` with no synchronization between them. `Shutdown` does not
  wait for the goroutine that called `Serve` to return, so the read can come
  before the write, and nothing orders them. The usual fix is a buffered
  `chan error` of size 1 that the goroutine sends on and `run` receives from.
  Left as is: it may be one of the deliberate bugs.
- Measured: `golangci-lint run` reports 6 errcheck issues on the starter. They
  are starter code, not findings.
- Production note: the handler for `POST /admin/shutdown` is open to anyone
  unless `ENV=production`. A kill switch keyed on an environment variable
  fails open when the variable is missing or misspelled. On a device or a
  shared host, bind admin endpoints to localhost or a separate listener instead.
